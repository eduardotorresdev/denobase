## Invariants

- Writes run hooks, zod validation (`fieldSchema` per field, then `CollectionConfig.schema`), unique/relation checks and
  realtime events, whichever surface called them (HTTP, store, factories).
- Realtime events leave only after commit (`afterCommit`); a delete's are built before the row goes.
- Side effects outside the db made inside a tx are undone through `afterRollback` (runs when the level or any level
  above it rolls back, commit failure included): a write's new uploads are deleted that way, as in PB's FileField.
- Views are read-only (`400 Unsupported collection type.`) and recreated from the snapshot after every migration batch.
- REST and realtime answer exactly like PocketBase (upstream source: github.com/pocketbase/pocketbase v0.39.10): status,
  message, data, framing.

- Identifiers reach SQL only via `quoteIdent`; values only as params.
- Auth collections get implicit columns `email`, `passwordHash` (hidden), `tokenKey` (hidden), `verified`.
- hasMany relationship/select and json are stored as JSON text.
- Errors cross HTTP as PB JSON `{status, message, data}`; engine throws `ApiError`.
- `_superusers`, `_otps`, `_migrations` and `_oauth_*` are system tables; only `_superusers` is a collection.
- Migrations never touch data; `up` and `genesis` refuse "multiple heads". Snapshots keep indexes sorted by name (order
  carries no meaning), and `addIndex` keeps a partial index's `where`.
- Thumbs (PB apis/file.go): `GET /api/files/...?thumb=<size>` with a size in `DEFAULT_THUMB_SIZES` (100x100) or the
  field's `thumbs`, on an original stored as png/jpg/jpeg/gif/webp, serves `<record dir>/thumbs_<file>/<size>_<file>`,
  generated on first request through the current BlobStore (so local, S3 and the files migration treat it as a record
  file). Sizes `WxH` (center crop), `WxHt`, `WxHb`, `WxHf` (fit, never enlarges), `0xH`, `Wx0`; jpeg stays jpeg, gif
  stays gif, anything else (webp, `image/jpg`) is PNG. Any other size or type, a decode failure, a source past
  `MAX_THUMB_SOURCE_PIXELS`/`_SIDE`, or no slot within 60s serves the original (warned). One generation per thumb key at
  a time, at most two decoding per storage, on a pool of two worker threads per process (a render past 30s terminates
  its worker). A file dropped by a write takes its `thumbs_<file>/` prefix with it, after its in-flight generations are
  canceled and awaited (a record delete does the same for its whole dir), so no thumb lands after the sweep.
- Uploads are stored inside the write's tx; files a write drops (or a deleted record's dir) go only after commit.
- `store.storage` is a `CurrentStorage`: `settings.s3` (enabled) points it at S3, else at the local storage the app was
  built with. No read fallback between them: a file on the old storage is 404 until migrated.
  `POST /api/settings/test/s3` (`filesystem: storage|backups`) writes and deletes a probe like PB.
  `POST /api/_denobase/s3/check` (superuser, not PB) checks an unsaved `{filesystem, s3}` draft in steps (connect, auth,
  bucket, write, read, cleanup) and may `suggest` a region or path style; an empty secret reuses the saved one of that
  filesystem only when the access key is the saved one.
- Files migration (`src/files/migrate.ts`): a `PATCH /api/settings` that changes the storage `settings.s3` names records
  the previous one as a `proposed` job (its credentials AES-GCM sealed with `DENOBASE_ENCRYPTION_KEY`, else a key in the
  data db's `_params`). A run copies record-file keys (`<collection>/<record>/...`) in sorted order with a cursor,
  skipping a destination key of the same size and overwriting any other; the destination is always the current storage
  (a run whose target changed fails). One running job (a partial unique index) owned by a 30s lease that a stalled run's
  resume takes over; cancel is a status change seen between keys. `deleteSource` deletes only at the end with zero
  failures. Superuser routes `GET|POST /api/_denobase/files-migration`, `GET .../plan` (dry run of the proposal: total,
  toCopy, same, bytes, from, to; null when none), `POST .../resume`, `POST .../cancel` (stable codes
  `files_migration_*`); progress on the realtime topic `FILES_MIGRATION_TOPIC`, superusers only. CLI
  `storage migrate --from local|s3 --to local|s3 [--delete-source] [--dry-run]` runs in its own process; `--to` must
  equal the current storage; old S3 creds via `--from-s3-*` or `DENOBASE_FROM_S3_*`; a running job is followed or taken
  over. Backups are not migrated.
- Multipart bodies (records, batch) never go through `Request.formData()`: `spoolMultipart` (`src/files/spool.ts`)
  streams each file part to a temp file and yields a `SpooledFile` (a `File` read back from disk). Only a file field's
  `maxSize` (PB default 5MB) is kept on disk; the rest is counted, so validation still fails with PB's
  `validation_file_size_limit`. Spool dirs belong to the request scope (`withSpoolScope` middleware) and are removed
  when it ends, stored or not.
- OAuth: the app is its own authorization server; codes, refresh tokens, session ids and client secrets are stored only
  as SHA-256, compared in constant time. A redirect goes only to a `redirect_uri` matched against the client's
  registration (loopback: any port). PKCE S256 is mandatory; `state` is optional and echoed back when sent. An access
  token with `gid` is checked against `_oauth_grants` on every `/api/mcp` request, so revocation is immediate; its
  scopes only narrow the tools access rules already allow. A code is spent only by its own client with the right
  verifier; replayed after that, it revokes its grant, and so does a reused refresh token (RFC 9700 §4.14). A pending
  request is bound to the browser that opened it (cookie) and its login forms carry its token. Remembered consent never
  skips the screen for a loopback redirect or a public client not configured in code. A web app session reaches a
  request only through `POST /oauth/handoff` (the app's own token) and a one-time code redeemed in that browser. A
  request signs in against the collection it was launched with (`auth_collection`), never one sent by a form; the pages
  never name it, and an account of another collection fails exactly like a wrong password or no account.
- OAuth web handoff, automatic: a request with no session of its own is sent once, before its login page, to the handoff
  page (`webLogin.url`, any origin; else the admin UI's `#/oauth-handoff` when `_superusers` may authorize), and
  `_oauth_requests.webTried` is set before it leaves, so it is never tried twice; `prompt=login` skips it. Contract of a
  consumer's handoff page: it receives `?oauth_txn=<txn>` and shows only a neutral loading state (no account, no
  collection, no error); with its own token it calls `POST <issuer>/oauth/handoff` with `Authorization:
  <token>` and
  `{ "txn": "<txn>" }` and replaces the location with the answered `url`; with no token, or on any non-200, it replaces
  the location with `<issuer>/oauth/authorize?txn=<txn>`. The issuer sends no CORS headers: a page on another origin
  reaches the endpoint through its own same-origin proxy. A code of another collection, spent, expired or redeemed in
  another browser ends on the same login page as no code. The answered `url` is built on `settings.meta.appURL`; the
  admin page follows only its path, on its own origin (where the binding cookie lives), so a wrong appURL in dev does
  not send the browser to another server.
- Settings persist in `_params` (`id = 'settings'`); secrets (smtp password, s3 secrets) never leave the server.
- Traces live in the auxiliary db too (`_spans`, one row per span); a trace is written whole once its local root ends,
  after sampling (head by trace id, tail keeps errors and slow ones). Library code only adds children to a trace
  something else started (request, cron run); `/api/traces*`, `/api/logs*`, `/_/`, health, realtime stream and
  `/api/_denobase/stats` never open one. A log written inside a trace carries `data.traceId`/`data.spanId`. The head
  decision is made when the root starts and travels in traceparent; an incoming traceparent is joined only with
  `traces.trustTraceparent`, and outgoing fetches send one only to `traces.propagateHosts`. A span dropped by the limit
  or `minDurationMs` has its children re-parented to the nearest kept ancestor. Error text on spans is scrubbed
  (e-mails, token values) and url.query masks sensitive keys. `_spans` is trimmed by age and by `MAX_SPAN_ROWS`, in
  chunks; spans of roots still open after terminate()'s drain are lost.
- Logs live in the auxiliary db (`pb_data/auxiliary.db`), apart from the data; backups zip `data.db`, `auxiliary.db` and
  the rest of pb_data except `backups/`.
- Heavy work runs in Web Workers (off the main thread): backup zip/extract and PB maintenance jobs. A worker opens its
  own SQLite connection by path; an in-memory db (tests) runs the same code inline.
